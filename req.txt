# 2. MIGRATION DATA MODEL

The migration has two major phases.

## Historical Load

The initial migration loads historical data according to a defined data scope.

Example:

Redshift may contain:

`2007 → 2026`

but the migration may only require:

`2017-01-01 → 2026-08-04`

The migration scope is defined using WHERE clauses in the existing Table Mapping List.

Example:

**Source WHERE:**

`lastchangedate BETWEEN '2023-02-17' AND '2026-08-04'`

**Target WHERE:**

`lastchangedate BETWEEN '2023-02-17' AND '2026-08-04'`

The reason for defining historical ranges is that source/target count mismatches were previously observed, and the team determined that the historical population being compared must have an explicitly defined scope.

Therefore, treat **Historical Data Scope Validation** as an important QA concern.

Some tables have no WHERE clause.

The behavior/meaning of a blank WHERE clause is still being confirmed with the project team.

Do NOT invent the expected behavior.

If relevant, mark it as:

**TBD / To Confirm**

until I provide the confirmed behavior.

# 3. DAILY INCREMENTAL LOAD

After the historical load, the tables will receive daily incremental data.

New records are identified using:

`etl_insert_timestamp`

Updated records are identified using:

`etl_update_timestamp`

Therefore, QA needs to independently validate:

* New records
* Updated records
* No unintended duplicate records
* No missed records
* Previously migrated historical data is not incorrectly affected

Do not confuse:

**Historical migration scope**

with

**Daily incremental loading**

They are separate QA concerns.
